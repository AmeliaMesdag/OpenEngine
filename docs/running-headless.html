Running the Player headless

The Player can run a project with no window, no graphics device, no audio device and no input device. The project's startup scene loads, its native and C# scripts, physics, pathfinding and the rest of the engine's systems run on a fixed step, and the log file is the only output. Terrain, ocean and skinned characters are the exceptions: see What does not run. Use it for a dedicated game server, a simulation or soak test, or any machine without a GPU. The engine has no networking module: a server brings its own transport, for example in a native script.

Command line

Player.exe --headless [--fixed-fps 60] [--quit-after <frames>] [--config <game.config>] [--asset-root <Assets folder>]
FlagMeaning
--headlessRun with no window, graphics device, audio device or input device.
--fixed-fps <rate>The headless step, in frames per second; 60 when not given. Without --headless (and outside movie capture) it is ignored, with a warning in the log. Each frame advances the simulation by exactly 1 / rate seconds and waits out the rest of its slot, so the game runs in real time. A frame that takes longer than its slot is not caught up.
--quit-after <frames>Exit after that many frames, in a headless or a windowed run. Without it the run lasts until a script asks to quit or the process is stopped. A value that is not a non-negative whole number is refused.
--config, --asset-rootAs for a windowed run: the game.config to load and the project's Assets folder. A packaged game finds both beside the executable.

For example, ten seconds of a project at 60 steps per second:

Player.exe --headless --fixed-fps 60 --quit-after 600 --config C:\MyGame\game.config --asset-root C:\MyGame\Assets

Ending the run from a script

A native (C++) script ends the run the same way the Player does for --quit-after: the frame finishes, the scripts' OnDestroy runs, and the process exits with code 0.

#include "Core/Application.h"

GameEngine::Application::Get()->RequestExit();

C# scripts have no quit call yet.

What does not run

Nothing is drawn: no render pipeline is loaded, the game UI is not built, and models and materials are not uploaded. Audio emitters play nothing. Keyboard, mouse and gamepad input reads as idle. Systems that only prepare rendering skip their work; game logic, physics and navigation over scene geometry run as they do in a windowed run.

Some simulation data is still produced only by the systems that prepare rendering, so a headless run does not have it yet:

  • Terrain gets no height data: it has no physics collider, nothing rests on it, and navigation that needs the terrain waits for it indefinitely.
  • Ocean buoyancy applies no forces, so bodies meant to float do not.
  • Skinned characters from the scene do not bind their skeletons, so they hold no animated pose.

A server for a game that relies on any of these needs to run windowed until that data is separated from rendering.

A flag that needs a graphics device is refused with an error that names the flag, and the Player exits with code 1:

  • --write-movie, --screenshot
  • --hdr, --hdr-mode, --hdr-bit-depth, --hdr-swapchain-bit-depth, --allow-hdr-toggle

HDR settings in game.config or the environment are ignored rather than refused: they describe the display a windowed run targets. Window-mode flags are ignored for the same reason.

Log and exit codes

The Player writes its log to %APPDATA%\<gameName>\Logs\game-<process id>.log, where gameName comes from game.config. Under a service account %APPDATA% is that account's profile, for example C:\Windows\System32\config\systemprofile\AppData\Roaming for LocalSystem.

Exit codeMeaning
0The run ended normally: --quit-after reached, or a script asked to quit.
1The command line or configuration was refused: --config names a missing file, a flag that needs a graphics device was given, --fixed-fps is not a positive number, or --quit-after is not a non-negative whole number. Restarting will not help; the log names the fix.
-1 (4294967295)Startup failed, for example the startup scene could not be loaded. The log line before Player: Failed to initialize names the cause.
-2, -3An unhandled exception ended the run; the log holds its message.
Stopping the process from outside (a service manager's stop, Task Manager) ends it immediately, without running script OnDestroy. A server that must persist state should save as it goes.

Restarting under a service manager

The Player is an ordinary program, not a Windows service, so it cannot be registered with sc create directly. A service wrapper such as WinSW registers it and restarts it when it exits with an error. A WinSW configuration that restarts the server five seconds after any failure:

<service>
  <id>MyGameServer</id>
  <name>My Game Server</name>
  <executable>C:\MyGame\Player.exe</executable>
  <arguments>--headless --fixed-fps 30</arguments>
  <onfailure action="restart" delay="5 sec"/>
</service>

Without a wrapper, a PowerShell loop does the same while a user stays logged on:

do {
    $p = Start-Process C:\MyGame\Player.exe -ArgumentList '--headless','--fixed-fps','30' -PassThru -Wait
    if ($p.ExitCode -eq 1) { break }   # refused arguments: fix the command line first
    Start-Sleep -Seconds 5
} while ($p.ExitCode -ne 0)
