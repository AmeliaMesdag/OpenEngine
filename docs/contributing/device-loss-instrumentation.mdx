What to arm, and in what order, when the engine takes a `VK_ERROR_DEVICE_LOST`. Scope is crash/hang forensics — for wrong-pixel debugging see the [GPU debugging guide](../rendering/gpu-debugging-guide.mdx).

:::caution[The constraint that shapes everything here]

This engine ships with `VK_EXT_descriptor_buffer` ON, and several standard instruments are partly or wholly disabled by it. Each entry below states explicitly whether it survives descriptor buffer, because an instrument that silently does nothing is worse than no instrument — its silence reads as a clean result.

:::

## What each instrument can and cannot see

| Instrument | Answers | Survives descriptor buffer? | Perturbs the app? |
|---|---|---|---|
| `VK_NV_device_diagnostic_checkpoints` :badge[existing]{variant=note} | WHERE execution stopped, at pass granularity | Yes | No — records a marker payload only |
| `VK_EXT_device_fault` :badge[added]{variant=success} | WHAT the hardware faulted on — address, access type, vendor code | Yes, and independent of checkpoint granularity | No — post-mortem query only |
| GPU-AV *buffer-content* checks :badge[added]{variant=success} | Malformed indirect draw/dispatch args, out-of-bounds indices | Yes — this half is not disabled | Yes — see the caveat below |
| GPU-AV *shader instrumentation* | Descriptor / BDA out-of-bounds inside shaders | No — force-disabled by the layer | n/a |
| DebugPrintf | Shader-side printf | No — force-disabled by the layer | n/a |
| Crash Diagnostic Layer :badge[external]{variant=note} | WHERE execution stopped, at *per-command* granularity | Yes — inserts buffer markers, touches no descriptors | Marker writes only; `sync_after_commands` does add barriers |

### Measured capability on the current dev machine

From `DeviceDiagnosticsTests` (headless, prints on every run — re-check rather than trusting this table on other hardware):

```text title="DeviceDiagnosticsTests probe lines"
[ probe    ] VK_NV_device_diagnostic_checkpoints advertised=yes available=yes
[ probe    ] VK_EXT_device_fault advertised=yes deviceFaultFeature=yes armed=yes
[ probe    ] VK_AMD_buffer_marker advertised=yes (crash-diagnostic-layer per-command granularity)
```

All three instruments are therefore available here, and because `VK_AMD_buffer_marker` is present the Crash Diagnostic Layer can use its buffer-marker path rather than falling back to checkpoints.

### Why checkpoints alone are not enough here

On this machine every queue family reports `checkpointExecutionStageMask = 0x2001` — `TOP_OF_PIPE | BOTTOM_OF_PIPE` and nothing else. A pass therefore reports only "started" and "finished". When a checkpoint dump brackets a fault as *the same pass at both stages*, the pass ran to completion and checkpoints cannot narrow the window further, no matter how many markers are added. That is a hardware/driver granularity limit, not a wiring gap — which is what motivates the other two instruments.

## Arming them

### Device fault — on by default in Debug/DebugFast, opt-in in Release

Enabled whenever the device advertises the extension and its `deviceFault` feature, and the config default says to ask for it. Retrieval costs nothing until a loss, so the developer configs keep it armed; a shipped build should not silently take on an extension nothing in it reads, so Release asks explicitly. `GE_VK_DEVICE_FAULT` overrides in both directions — `=1` arms a Release investigation, `=0` disarms a developer build to A/B whether the extension itself changed anything. Startup logs exactly one of:

```text title="The three startup states"
VulkanDevice: VK_EXT_device_fault ARMED — a device loss will report fault address/vendor records automatically
VulkanDevice: VK_EXT_device_fault NOT REQUESTED (opt-in in this config) — ... set GE_VK_DEVICE_FAULT=1 to arm it
VulkanDevice: VK_EXT_device_fault unavailable — device-lost reports will carry no faulting-address records
```

"We did not ask" and "the device cannot" are different facts, and after a loss it is too late to work out which one you had.

On a loss, after the checkpoint dump:

```text title="A device fault report"
VulkanDevice: device fault records: description='...'; address records (N): [0] WRITE_INVALID
  reported=0x00000000deadb000 precision=4096 range=[0x00000000deadb000,0x00000000deadc000);
  vendor records (M): [0] '...' code=0x... data=0x...
```

:::note[Match on the range; treat the reported address as an extra hint]

Reported addresses are precise only to a power-of-two granule (`addressPrecision`). The half-open `range=[begin,end)` is the set of GPU virtual addresses one of which faulted, and is what you match against a buffer's device address. The spec also allows a driver to report a *more* precise address than its stated precision, in which case `reported=` is a valid additional hint — which is why both are printed.

:::

:::note[Reading the trailing NOTE]

The retrieval is a two-call protocol and `VK_INCOMPLETE` has three independent causes, so the report names which one fired rather than asserting that records were lost:

- `NOTE: records TRUNCATED (n/m address, n/m vendor)` — records were genuinely lost. If it adds `— capped at 256 records per array`, *we* dropped them: the driver reported an implausible count and the request was capped rather than allowed to allocate unbounded inside the crash handler.
- `NOTE: all records retrieved; driver also holds an N-byte vendor binary
 crash dump (not requested...)` — **nothing was lost.** The vendor blob is declined on purpose (it needs a vendor offline tool), and declining it returns `VK_INCOMPLETE` by itself. Since `deviceFaultVendorBinary` is not enabled, a conformant driver should report 0 here, so a nonzero size also says something about the driver.
- `NOTE: driver returned VK_INCOMPLETE but reported nothing short` — the driver's record counts moved between the sizing and retrieval calls, which the spec forbids. Records may be missing that these numbers cannot name.
- No NOTE at all — everything the driver had was retrieved.

:::

If the extension is unavailable, or the loss was synthesized (fault injection or the hung-escalation cap, neither of which puts the device in the *lost* state that `vkGetDeviceFaultInfoEXT` requires), the loss path says so explicitly rather than printing nothing — an absent report is never mistaken for a clean one.

### GPU-AV buffer-content checks — `GE_VK_GPU_AV=1`

Off by default. It also needs the validation layer actually *loaded*, which DebugFast does not do by default — set `GE_VK_VALIDATION=1` alongside it, or the run reports nothing at all. Startup states whether it actually engaged; if it did not, it says that too, and names this as the likely reason.

```bat title="Arm GPU-AV buffer-content checks"
set GE_VK_VALIDATION=1
set GE_VK_GPU_AV=1
```

What it covers, and what it deliberately does not:

- :badge[covered]{variant=success} indirect draw arguments (`VkDrawIndirectCommand`, `VkDrawIndexedIndirectCommand`)
- :badge[covered]{variant=success} indirect dispatch arguments (`VUID-VkDispatchIndirectCommand-x/y/z-00417/18/19`)
- :badge[covered]{variant=success} indirect trace-rays arguments (no consumer in this engine today — it comes with the family)
- :badge[covered]{variant=success} index buffers — indices within the index buffer, and within the fetched vertex buffers
- :badge[covered]{variant=success} buffer copies
- :badge[not covered]{variant=danger} descriptor out-of-bounds, buffer device address out-of-bounds, ray-query validation, DebugPrintf — all shader-instrumentation checks, all disabled while `VK_EXT_descriptor_buffer` is *enabled on the device*. The gate is the extension being enabled, not this engine using it: `GE_VK_USE_DESCRIPTOR_BUFFER=0` only flips the runtime path and leaves the extension enabled, so it does not restore them, whereas `GE_VK_CAPTURE_COMPAT=1` drops the extension and does. Request them with `GE_VK_GPU_AV_SHADER_INSTRUMENTATION` (default `auto` — asked for exactly when the extension is ruled out)

Each of those five checks is requested explicitly, not inherited. The layer reads the `gpuav_buffers_validation` parent and, when it is true, then reads the five individually — so pinning only the parent would leave each check governed by its own default, and a default flip would empty the instrument while the parent still reported the family as enabled.

:::danger[GPU-AV perturbs the state it measures]

It inserts a validation dispatch ahead of each indirect command using its own pipeline and normal descriptor sets. Its `RestorablePipelineState` (`gpuav/core/gpuav_validation_pipeline.cpp`) restores pipeline, descriptor sets, push constants and rendering state — but has *no handling of `VK_EXT_descriptor_buffer` bindings*. Under descriptor buffer the app's descriptor-buffer offsets are therefore not re-established after an inserted dispatch. Treat GPU-AV findings as leads to corroborate against a `GE_VK_GPU_AV=0` run, never as standalone proof, and treat a *new* failure mode under GPU-AV as possibly the instrument's own.

:::

### Crash Diagnostic Layer — per-command granularity, zero engine changes

Ships with the Vulkan SDK as `VK_LAYER_LUNARG_crash_diagnostic`. It is registered as an **explicit** layer, so `VK_CRASH_DIAGNOSTIC_ENABLE=1` alone will not load it — force it on through the loader:

```bat title="Load the Crash Diagnostic Layer"
set VK_LOADER_LAYERS_ENABLE=VK_LAYER_LUNARG_crash_diagnostic
set CDL_OUTPUT_PATH=C:\Dev\_cdl
set CDL_INSTRUMENT_ALL_COMMANDS=true
set CDL_DUMP_COMMANDS=all
set CDL_DUMP_SHADERS=on_crash
set CDL_TRACK_SEMAPHORES=true
set CDL_WATCHDOG_TIMEOUT_MS=10000
```

It writes a dump naming the command buffers that were executing and the exact command each had reached. It reports its own capability at startup, and the messages to check for are:

```text title="The layer's capability messages"
No VK_NV_device_diagnostic_checkpoints or VK_AMD_buffer_marker extension, progression tracking will be disabled.
No VK_AMD_buffer_marker extension, semaphore tracking will be disabled.
No VK_EXT_device_fault extension, vendor-specific crash dumps will not be available.
```

:::caution[Check which marker mechanism it picked]

With `VK_AMD_buffer_marker` it writes a per-command marker value and gets true per-command resolution. Falling back to NV checkpoints inherits the same `0x2001` stage limit described [above](#why-checkpoints-alone-are-not-enough-here) and buys much less. If the first message above appears, the layer is tracking nothing and its silence means nothing.

:::

`CDL_INSTRUMENT_ALL_COMMANDS=true` is expensive; it is a forensic mode, never a default. `CDL_SYNC_AFTER_COMMANDS` adds a barrier after each instrumented command — it sharpens attribution but changes scheduling, so a fault that disappears under it is evidence of a synchronization bug, not a fixed one.

## Suggested order for a device-loss investigation

1. **Read the existing loss log first.** Checkpoints plus device fault are already armed and cost nothing. If the fault records name an address, correlate it with buffer device addresses before adding any instrument.
2. **If the fault window is a single pass that both started and finished**, checkpoints are exhausted — go to per-command granularity with the Crash Diagnostic Layer rather than adding more markers.
3. **If the suspect pass consumes GPU-written indirect arguments or an index buffer**, run `GE_VK_GPU_AV=1`; that is exactly the check that is otherwise missing, and it produces a VUID rather than a silent fault. Corroborate any hit against a control run.
4. **Only then reach for RenderDoc.** A capture of a run that device-losses is often unobtainable; the passive instruments above survive the loss, which is why they come first.
